## Matching methodology

Deliberately strict — no fuzzy matching, to avoid inflating scores:

- **Normalization**: case-insensitive, whitespace-collapsed, trimmed.
  Nothing else — no punctuation stripping, no date parsing. `"2021"` and
  `"2021 "` match; `"2021"` and `"Jan 2021"` do not.
- **Singular fields** (full name, email, phone): both absent = true
  negative, not counted. One side present = one FN or FP. Both present
  but different = counted as **one FP and one FN** (standard IE
  convention: a wrong answer is both a missed right answer and a produced
  wrong one).
- **Repeatable fields** (links, job titles, companies, dates, degrees,
  institutions, raw skill mentions) are matched as a **normalized
  multiset** — exact string match, order-independent, duplicate-count
  aware, via greedy consumption. This is **not** tied to a specific
  experience/education entry index, so a re-ordered layout (e.g. the
  two-column fixture) isn't penalized for order. The tradeoff: a title
  extracted correctly but attached to the wrong company within the same
  fixture would not be caught — see Limitations.
- **Skill normalization accuracy** is computed only over raw mentions
  that were themselves correctly extracted (true positives). Normalizing
  a skill the pipeline never found isn't a meaningful question. A
  "correct" mapping means an exact match of canonical names, including
  both sides legitimately being "unmatched" (`None`).

## Confidence sanity check (NOT calibration)

151 scored field-level data points across 10 fixtures (149 before the
links fix; the 2 newly-extracted links add 2 more correct samples).
Heuristic confidence values here are **not probabilities** — this only
asks whether `needs_review` behaves sensibly relative to actual
correctness.

- Mean confidence of correct (TP) fields: **0.818**
- Mean confidence of incorrect (FP) fields: **0.776**

These are close together and the incorrect-field mean is pulled down
almost entirely by one low-confidence case; with 8 incorrect samples this
difference is not meaningful on its own. The links fix did not touch any
incorrect sample -- the incorrect-field numbers below are unchanged from
before the fix.

- Correct fields flagged `needs_review=True`: **22 / 143** (expected and
  fine — these are fields the scorer was right to flag as needing a
  human look even though the extraction happened to be correct, e.g.
  every heuristic-detected full name).
- **Incorrect fields NOT flagged `needs_review`: 7 / 8.** This is the
  important number. Of the 8 false-positive extractions in this set,
  7 carried `needs_review=False` — the heuristic confidence scorer
  presented them as fine. Every one of the 5 table-header/rating-cell
  skill noise items ("Skill", "Level", "Expert", "Advanced",
  "Intermediate") scored 0.85/`needs_review=False`; the "systems"
  keyword-collision company and the "M.S"/"M.S." punctuation mismatch did
  too. Only the `table_resume.pdf` "Skill"-as-a-name false positive was
  correctly flagged (confidence 0.16).

**Read honestly**: on this small sample, the confidence heuristic does
**not** reliably catch wrong extractions that came from a *confident
extraction method being pointed at the wrong text* (an exact Skills-list
match, a suffix-keyword hit, a clean regex match) — it mainly reflects
"was the extraction *method* strong," not "is the resulting *value*
correct." That's a real, useful finding for how much weight to put on
`needs_review` alone versus a recruiter's own read of the source
evidence. Eight data points is nowhere near enough to generalize beyond
"this specific failure mode exists," which is exactly what it shows.

## Major findings

**A: Genuine gap, found and FIXED.** Contact links on their own line (no
email/phone on that line) were never classified into the Contact section
at all — segmentation's content-based Contact detection
(`segmentation/segmenter.py`) only checked for an `EMAIL_RE`/`PHONE_RE`
match. `ContactInfo.links` was therefore unreachable in that (common)
resume layout. Verified directly: `varied_formats_resume.pdf` has two
real links on their own line; both ended up in `unclassified_text`, and
`links` came back empty. **Fixed**: the same content-based check now also
tests `URL_RE` (already used elsewhere in the codebase for link
extraction), under the identical guard used for email/phone, so it
cannot fire once any heading has been seen. Four regression tests added
in `tests/unit/test_segmentation.py`; see the "Post-fix update" section
above for the before/after numbers. No other category regressed.

**B: Known, already-documented limitation, reconfirmed.**
`table_resume.docx`'s Skills-section table takes header/rating cells at
face value ("Skill", "Level", "Expert", "Advanced", "Intermediate" all
become skill candidates) — this matches the top-level README's existing
Limitations entry exactly; validation just puts a number on it (5 FPs,
all the false positives in the skills category).

**C: Two small, real extraction quirks, newly surfaced.**
- `table_resume.pdf` (a bare table with no other content): the header
  cell "Skill" is the very first block with no preceding heading, so the
  name-shape heuristic (short, capitalized, no digits) misfires and
  produces a false `full_name`.
- `two_column_resume.pdf`: the free-text line "Built distributed
  systems." contains the ordinary word "systems," which collides with
  the company-suffix keyword list (`_COMPANY_SUFFIXES` includes
  "systems," meant for names like "Acme Systems"), so the whole sentence
  is misclassified as a company — confidently (`section_heuristic`,
  `exact`, not flagged for review).
- `varied_formats_resume.pdf`: the abbreviated-degree regex drops a
  trailing period (`"M.S."` → `"M.S"`) — cosmetic, not a wrong degree.

## Limitations of this evaluation

- **10 fixtures is a demonstration set, not a powered sample.** Every
  percentage above should be read as "this is what happened on these 10
  documents," not "this is the system's accuracy."
- **All fixtures are synthetic** (`tests/fixtures/README.md`) — clean
  synthetic text likely understates real-world noise (OCR artifacts,
  inconsistent spacing, unusual real-world phrasing).
- **Multiset matching is not entry-aware.** A job title correctly
  extracted but attached to the wrong company within the same fixture
  would score as two independent correct fields, not one broken
  association. None of the errors found here were actually of this
  shape, but the methodology as defined would not catch it if one
  existed.
- **Skill normalization accuracy is scoped to already-correct
  extractions** (by design, see Matching methodology) — it says nothing
  about normalization behavior on skills the extractor missed entirely.
- **The confidence sanity check is 8 incorrect data points.** Real, but
  not enough to generalize a rate from.
- **No calibration claim of any kind is made anywhere in this
  document.** The heuristic confidence model (`confidence/scorer.py`) is
  an engineering heuristic; nothing here converts it into or evaluates it
  as a calibrated probability.
